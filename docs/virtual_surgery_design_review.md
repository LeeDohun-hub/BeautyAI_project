# 가상 성형 설계안 — 코드 대조 검토

대상: [virtual_surgery_recommendation_design.md](virtual_surgery_recommendation_design.md) (2026-08-03)
검토일: 2026-08-03 · 방법: 현재 저장소 코드와 1:1 대조

문서의 방향(의료 단정 회피, 상담 후보 중심, 비율조정 제외)에는 동의한다.
아래는 **코드와 어긋나는 지점**만 추렸다.

## 1. 이미 구현된 것을 "앞으로 할 일"로 적고 있다 ★

문서 §12는 "MVP에서는 새 `.pt` 를 학습하지 않아도 되며, MediaPipe Face Mesh 등을 활용해
시작할 수 있다" 라고 쓰고 있다. **이미 그렇게 돌아가고 있다.**

| 문서가 "앞으로" 라고 쓴 것 | 실제 코드 |
|---|---|
| 얼굴 랜드마크/CV 모델 도입 | `app/services/face_shape_analyzer.py` — MediaPipe Face Mesh 468점, `refine_landmarks=True` |
| 얼굴 비율/윤곽 분석 | 같은 모듈의 `analyze()` |
| AI 미리보기 생성 | `app/services/virtual_surgery_simulator.py` — 얼굴 외곽 워프 + 코 하이라이트 + 잡티 소프트닝 |
| API | `POST /api/virtual-surgery/simulate` (routes.py:950) |
| 화면 | `App.tsx` '가상 성형 추천 시스템' 6단계 |

**영향**: 이 문서를 그대로 로드맵으로 쓰면 이미 있는 것을 다시 만든다.
§13 MVP 항목을 **"신규 / 이미 있음 / 수정"** 으로 다시 분류해야 한다.

## 2. §6 "비율조정 슬라이더 MVP 제외" 는 **추가가 아니라 삭제** 작업이다 ★

`App.tsx:4316`:

```js
const flowSteps = ['개인정보 입력', 'AI 성형 분석', '얼굴형 분석결과',
                   '개선 얼굴형 선택', '비율 조절', '결과지 출력'];
```

'비율 조절' 단계가 **이미 있다.** 문서는 이걸 빼라고 한다 — 즉 기존 기능 제거 결정이다.
문서에 "제외"라고만 적혀 있으면 신규 스코프에서 뺀 것으로 읽히므로, **"기존 단계 삭제"**
로 명시해야 한다. 삭제인지 비활성인지도 정해야 한다(고객사 데모에서 이미 보여준 화면이면 되돌리기 부담).

## 3. §12의 "기존 `.pt` 를 피부 분석에 재사용" 은 **현재 모델이 못 준다** ★★

문서는 얼굴 비율에 피부/PC 모델을 쓰지 말라고 정확히 선을 그었다. 여기까지는 맞다.
문제는 **재사용하라고 한 쪽**이다.

`app/ai/skin_model.py`:
```python
TARGETS = ("acne", "pore", "wrinkle", "redness", "pigmentation", "oiliness")
```

6채널로 보이지만 **실측상 6개를 구분하지 못한다** — 학습 라벨이 동일해 `pore`와 `wrinkle`이
사실상 같은 값이고 출력 채널 간 상관이 0.95+ 다. 그래서 서비스는 이미 **3그룹·3구간 표시**로
해상도를 낮춰 쓰고 있다.

그런데 설계안은:
- §5 분석 항목에 "피부결 / 잡티 / 톤 균일도"를 **별개 항목**으로 두고
- §7 결과지에 "피부 시술 후보"를 세분해 요구하고
- §9에서 "피부과/쁘띠 시술 상담 후보"를 따로 분류한다

**모델이 못 주는 해상도를 문서가 전제하고 있다.** 이대로 만들면 "모공 시술 후보 / 주름 시술
후보"를 근거 없이 갈라 놓게 되고, 이건 §10이 금지한 단정에 정확히 해당한다.

**권고**: 피부 관련 서술을 현재 모델이 실제로 구분하는 단위(3그룹)로 낮추거나,
성형 리포트에서는 피부를 "피부 상태는 별도 분석 참고" 수준으로만 링크한다.

---

## 4. §10 안전장치가 **이미 있는 자산을 안 쓴다** ★★

`data/models/derma_tier1_gate.pt` / `derma_tier2_classifier.pt` — **피부질환 2단 선별기**가
이미 있다(설정: `derma_tier1_model_path`, `derma_tier2_model_path`).

문서 §10의 "건강정보 리스크가 있는 경우 상담 우선 안내"는 이 모델이 담당해야 할 자리인데
설계안 어디에도 언급이 없다. 미용 목적으로 올린 얼굴 사진에 질환 소견이 있으면
**미용 상담 후보보다 그쪽을 먼저 안내**하는 게 안전 설계의 핵심인데 빠져 있다.

**권고**: §9 추천 로직의 1~2단계 사이에 "질환 선별 게이트"를 넣고, 걸리면 개선 방향 카드
생성을 중단하거나 문구를 바꾼다.

---

## 5. §12 "diffusion 이미지 편집 모델 도입" 은 재고 권장 ★

현재는 랜드마크 기반 **보수적 워프**다(원본 픽셀 보존, 변형 위치가 결정론적).
문서는 이걸 "충분하지 않다"며 diffusion face editing 을 후보로 든다.

의료 맥락에서는 **지금 방식이 더 안전하다**:
- 원본을 보존하므로 "실제 결과 예측"으로 오해될 여지가 적다
- 같은 입력에 같은 출력 — 재현 가능하고 근거를 설명할 수 있다
- diffusion 은 **얼굴 정체성이 바뀌거나 없던 특징을 만들어낸다**. §10의 "결과를 보장하지
  않습니다" 고지와 정면으로 충돌할 위험이 크다(사용자는 그림이 예쁘면 그걸 결과로 받아들인다)
- 비용·지연도 다르다(현재는 서버 내 CV 연산, diffusion 은 GPU 추론 or 외부 API 과금)

**권고**: "고도화 = diffusion" 을 기정사실로 두지 말고, 먼저 현재 워프의 **변화 강도 3단계**를
붙여보고 부족한 지점을 확인한 뒤 결정한다.

## 6. 일본 시장이 통째로 빠져 있다 ★★

서비스는 이미 `jp.yopalette.com` 으로 일본몰을 운영 중이고, AI 앱도 ko/ja 이중 언어다
(`frontend/src/i18n.ts`).

설계안에는 다국어 언급이 없고, §17 참고 기준이 **미국 자료뿐**이다(ASPS / Mayo / FDA).

- 한국: 의료법 제56조(의료광고) — "상담 후보" 표현으로 안전하다고 **단정할 수 없다**
- 일본: 医療広告ガイドライン — 비포/애프터 이미지 취급에 별도 규제가 있다.
  **AI 미리보기가 정확히 그 형태다**

**권고**: §17에 한국·일본 기준을 추가하고, "법무 확인 필요" 를 미해결 항목으로 명시한다.
일본어 문구는 i18n 사전에 성형 관련 키를 추가해야 한다(현재 거의 없음).

## 7. §11 개인정보 — 추적 결과(2026-08-03 확인 완료)

문서는 확인 없이 "기본값은 분석 후 즉시 삭제" 라고만 적었다. 실제로 어디까지 남는지 추적했다.

**남지 않는 것 — 설계안이 걱정한 것들은 대부분 이미 안전했다**

| 경로 | 결과 |
|---|---|
| 업로드 이미지 → 디스크 | **저장 안 함**(`app/` 전체에 이미지 파일 쓰기 없음) |
| 이미지 바이트 → DB | **저장 안 함** |
| 프론트 localStorage/sessionStorage | **저장 안 함** |
| 외부 전송(OpenAI 등) | 이미지는 안 보냄(챗은 텍스트만) |
| 응답의 `original_image`/`preview_image` | data URL — 브라우저 메모리에만 |
| 장바구니 핸드오프의 `image_url` | **상품** 이미지지 얼굴 사진이 아님 |

**남던 것 — 하나 있었고 고쳤다**

`skin_analyses.image_name` 에 **업로드 원본 파일명**이 그대로 들어가고 있었다. 그런데
이 컬럼은 **코드 어디서도 읽지 않는다**(쓰기 1곳, 읽기 0곳). 즉 쓰지도 않는 값이
`user_id` 와 묶여 무기한 남아 있었다.

로컬 DB 실측 — 정확히 우려하던 형태였다:

```
id=1: 'KakaoTalk_20260622_153024335.jpg'   ← 출처(카카오톡) + 촬영 시각
```

파일명에는 이름·날짜·기기·장소가 들어가는 일이 흔하다("2026-08-03 김OO 병원상담.jpg").

- 수집 중단: `routes.py` 가 **확장자만** 남긴다.
- 기존 데이터: `scripts/scrub_image_names.py` (`--dry-run` 먼저, 재실행 안전).

**남은 판단(코드가 아니라 정책)**

- 분석 점수(`skin_analyses`)와 추천 이력은 계정에 계속 쌓인다. 얼굴 사진 자체는 아니지만
  **피부 상태 이력**이라 민감도가 있다. 보관 기간·삭제 요청 경로는 정해진 게 없다.
- 설계안 §11 의 "저장 시 보관 기간 명시 / 사용자 삭제 요청" 은 **아직 없는 기능**이다.

## §13 MVP 재분류 — '신규 / 이미 있음 / 삭제' (2026-08-03 기준)

설계안의 MVP 목록은 전부 '앞으로 만들 것'처럼 적혀 있었다. 실제 상태로 다시 나눈다.

| 설계안 항목 | 실제 | 비고 |
|---|---|---|
| 기본정보 및 목표 설정 | **있음** | 2026-08-03 복수선택+우선순위로 개선 |
| 개선 부위 복수 선택 | **있음(신규)** | 최대 3개, 순서=우선순위 |
| 원하는 변화 이미지 복수 선택 | **있음(신규)** | 최대 2개(모순 조합 방지) |
| 정면 사진 1장 업로드 | **있음** | |
| 사진 품질 확인 | **부분** | 정면 이탈만 판정(`_frontal_offset`). 조도·가림·해상도는 없음 |
| 얼굴 비율 분석 | **있음** | `face_shape_analyzer`(Face Mesh 468점) |
| 개선 방향 카드 3개 | **있음(4개)** | `CARD_PRESETS` — 백엔드가 단일 출처 |
| AI 미리보기 3개 | **있음(4개)** | `/virtual-surgery/preview-cards` |
| 카드별 변화 강도 3단계 | **있음(신규)** | natural/balanced/defined |
| 상담용 결과지 화면 | **있음** | |
| 부위별 비율조정 슬라이더 | **삭제함** | '2차로 미룸'이 아니라 **기존 기능을 제거**한 것 |

**아직 없는 것(진짜 신규)**
- 사진 품질 게이트의 나머지(조도·가림·해상도·필터)
- 상담 질문 리스트 자동 포함(§16)
- 비용/회복기간 범위(§7) — 데이터 소스가 없다
- 시술 후보의 4분류(메이크업/쁘띠/성형외과/수술) — 지금은 3개 카드에 섞여 있다
- 보관 기간 자동 만료(§11) — 삭제 수단은 `DELETE /api/me/data` 로 만들었다

| 순위 | 항목 | 이유 |
|---|---|---|
| 1 | §13 MVP 를 "신규/기존/삭제" 로 재분류 | 지금 문서로는 뭘 만들지 알 수 없다 |
