# 바디 상품 카테고리 기준 (확정: 2026-07-24)

`docs/CODEX_HANDOFF_20260723_body_reco.md` §4에서 미결이던 3안 중 **3안(바디 크롤 프로젝트)**
으로 확정하고, 수집·분류 기준을 이 문서로 고정한다.

사용자 확정 사항 3가지:

1. **쇼핑몰 카테고리 전체를 가져오되 섞이지 않게 한다.** 데오드란트·제모까지 수집하되,
   질환 기반 추천에 올라가는 카테고리는 따로 구분한다.
2. **핸드·풋은 바디와 분리한다.** "전혀 다른 제품일 수 있음" — 매니페디큐어 기능이 가져갈
   그룹이라 바디 추천에 섞이면 안 된다.
3. **전 소스 수집** (올리브영 글로벌/KR, 마츠키요, 아마존 US/JP/HF).

## 1. 카테고리 정의

값은 항상 `<group>.<form>` 형태다. 정의는 `backend/app/services/body_categories.py` 한 곳에만 있다.

| foot | `foot.deodorant` | 발 데오드란트 | ❌ |

### 왜 네임스페이스인가

얼굴 카테고리는 접두사 없는 값(`cream`, `lotion`, `serum`)을 쓴다. 접두사를 붙이면
**문자열이 구조적으로 절대 겹치지 않는다.** 얼굴/바디가 같은 `"cream"`을 공유하던 게
기존 사고의 원인이었다(`recommender.BODY_CARE_CATEGORIES = {"cream","lotion",...}`).

### 로션과 크림을 왜 나누나

`recommender.py`의 보습 조립이 **피부타입으로 로션/크림 택1**을 한다(face·body 공용).
둘을 합치면 그 로직을 바디에 재사용할 수 없다.

## 2. 분류 기준

### 원칙: 공식 카테고리 우선, 키워드는 폴백

이름 키워드만 쓰면 **올리브영 공식 `Bath & Body` 106건 중 55건을 놓친다**(실측).
놓치는 게 하필 대표 상품이다 — `ILLIYOON Ceramide Ato Lotion`, `ILLIYOON Ultra Repair Cream`
은 이름에 "body"가 없다. 아토피·습진 추천의 핵심 상품이 통째로 빠진다.

| 소스 | 공식 카테고리 | 판정 방식 |
|---|---|---|
| 올리브영 글로벌 | ✅ `Bath & Body` 6개 서브 + `Wellness > Foot Care` | 카테고리가 그룹 결정 → 이름으로 제형만 세분화 (`classify_within_group`) |
| 올리브영 KR | ❌ 검색 크롤 | 키워드 (`classify_by_keyword`) |
| 마츠키요 | ❌ 크롤 경로가 `cat:004`(스킨케어 트리) | 키워드. 일본어는 제형 표기가 명시적이라 잘 듣는다 |
| 아마존 US/JP/HF | ❌ 없음 | 키워드 + 배제 규칙 |

**공식 카테고리는 키워드가 뒤집지 못한다.** 제형을 못 찾으면 서브카테고리 기본값을 쓴다.

### 배제 규칙 (키워드 소스에만 적용)

실측된 오탐을 근거로 만든 것이다.

| 규칙 | 잡는 오탐 |
|---|---|
| 립·색조·헤어·도구·구강 배제 | 레브론 **립** 슈가스크럽 → `body.scrub`, CURL KEEPER **헤어** 드라이오일 → `body.oil`, 레브론 속눈썹**뷰러** → `hair_removal` |
| 얼굴 제형 표기 + 겸용 표기 없음 → 배제 | COSRX **얼굴** 크림이 SEO 꼬리표에 `ボディローション ボディクリーム`를 달아 `body.cream`으로 잡히던 것 |
| 선케어 표기 + 바디 언급 없음 → 배제 / 있으면 `body.sun` | d'Alba·SOME BY MI **얼굴 선크림**이 `body.lotion`으로 잡히던 것 |
| 괄호 안 증정품 제거 후 판정 | `ILLIYOON MD Red Itch Care Cream (+Red Itch Oil 20mL)` → 증정 오일 때문에 `body.oil`이 되던 것 |
| 제형 선택은 **매치 위치**로 (규칙 순서 아님) | `Body Lotion ... Body and Hand Lotion` → `hand.cream`으로 잡히던 것 |

회귀 테스트: `backend/tests/test_body_categories.py` (10 케이스군).

## 4. 섞임 방지 경계 (코드에 반영됨)

네임스페이스만으로는 부족해서 게이트 2개를 막았다. 둘 다 실측 누수가 있었다.

1. **`recommender.recommend_products` 얼굴 분기** — 얼굴 경로는 카테고리 화이트리스트 없이
   DB 전체를 점수화한다. 바디 카탈로그를 적재한 순간 바디워시가 얼굴 Top5에 올라온다.
   → `NON_FACE_CATEGORIES` 체크 추가.
2. **`routine_steps.classify_routine_step`** — `_STRONG_NAME`(이름 신호)이 카테고리 검사보다
   **먼저** 돈다. 실측 16건 누수: `ILLIYOON Ceramide Ato 5.0 Gentle Skin Cleanser`가 얼굴
   클렌저 컬럼으로, 바디 선크림이 얼굴 선크림 컬럼으로 갔다.
   → 함수 최상단에서 네임스페이스 차단.

## 5. 알려진 한계

> **2026-07-24 갱신**: 아래 성분 제약은 KR 상품에 한해 해결됐다. §7 참조.

### 성분 데이터가 없다 (가장 큰 제약)

- 케어 카테고리 273건 중 **이름에서 성분이 검출되는 건 50건(18%)** 뿐이다.
  (Ceramide 35 · Salicylic Acid 5 · Centella 4 · Panthenol 3 · 기타)
- 올리브영 글로벌 상세 API(`/product/detail-data`, 93필드)에 **전성분 필드가 없다**(실측).
  `notiCont`(상품고시정보)도 `None`. 성분 확보는 상세 HTML 스크래핑 등 별도 작업이 필요하다.
- **성분을 지어내지 않았다.** 옛 `scripts/load_body_products.py`는 성분 미검출 시
  `["Panthenol", "Ceramide"]`를 그냥 채워 넣었는데, 그러면 추천 이유에 "2개 바디 진정 성분"
  이라고 표시되는 제품이 실제로 그 성분을 가졌는지 아무도 확인한 적이 없게 된다.
  새 로더는 검출된 성분만 붙이고 없으면 성분 없이 적재한다.

→ **이것이 추천 로직 설계를 규정한다.** 성분 교집합을 하드 게이트로 쓰면 273건 중 50건만
살아남는다. 카테고리·질환 적합도로 랭킹하고 성분은 가점으로 쓰는 구조가 필요하다.

### 소스별 미수집분

- **마츠키요**: 현재 데이터는 `cat:004`(스킨케어 트리) 크롤의 부산물이다. 바디 카테고리를
  직접 크롤하면 크게 늘어난다. 단 JP 이그레스 IP + 느린 페이싱 필요(`crawl_matsukiyo.py` 참조).
- ~~**올리브영 KR**: 바디 검색어가 없다~~ → 2026-07-24 `--body` 시드 추가로 해결
  (39 → 349건). curl_cffi 로 통과됐고 헤드풀 브라우저는 필요 없었다.
- **이미지**: KR 검색 API 가 이미지를 안 줘서 커버리지가 62% 다. `enrich_product_images.py`
  로 보강해야 카드가 제대로 나온다.
- **`body.sun` 30건**은 얼굴 겸용 선크림이 다수다(`顔 全身用` 표기). 질환 추천 대상이
  아니라서 영향은 없지만 카탈로그 표시용으로 쓸 땐 감안할 것.

## 6. 추천 로직 (2026-07-24 반영)

### BODY_SLOTS — 얼굴 5슬롯을 바디에 쓰지 않는다

바디엔 토너·세럼 개념이 없고, 얼굴 슬롯을 그대로 쓰면 `classify_routine_step` 이 `body.*` 를
모르니 컬럼이 **전부 얼굴 제품으로 찬다**(핸드오프 문서가 지적한 그 문제).

| 슬롯 | 카테고리 | 비고 |
|---|---|---|
| `body_wash` 바디 세정 | `body.wash` | |
| `body_moisturizer` 바디 보습 | `body.lotion` / `body.cream` | 지성·복합→로션, 그 외→크림 우선(얼굴 보습 슬롯과 같은 규칙) |
| `body_treatment` 바디 집중케어 | `body.treatment` / `body.oil` | |

`BODY_CATALOG_CATEGORIES` 에 미스트·데오드란트·제모·선케어와 `hand.*`/`foot.*` 는 없다.
카탈로그로는 갖되 질환 추천엔 올리지 않는다.

### 성분: 하드 게이트 → 가점

성분 교집합을 필수 조건으로 걸면 케어 435건 중 164건만 남는다. 그래서 **일치는 가점**으로
쓰고, 정렬 키를 `(성분일치수, 성분정보유무, 피부타입적합, 평점, 플랫폼)` 으로 둔다.
성분이 확인된 상품이 항상 위로 오되, 미상 상품이 통째로 사라지진 않는다.

**단 `avoid` 목록이 있는 질환(습진·아토피 등)은 예외로 성분이 확인된 상품만 쓴다**(`strict`).
성분을 모르면 자극 성분 검사 자체가 불가능해서, 레티놀 바디로션을 아토피에 추천하는 사고가
난다.

### 자극 성분 배제는 2중이다

성분 데이터가 없는 상품이 아직 많아서 성분표만 보면 샌다. **상품명도 같은 별칭 테이블로
검사**한다(`detect_ingredients_ko(product.name)`).

실측 사고 2건이 근거다:

1. `힐그리즈 레티노이드 0.1% 퍼밍 바디 세럼` — 전성분이 **하이드록시피나콜론레티노에이트**라
   '레티놀' 검색에 안 걸려 습진 추천에 올라왔다.
2. `베타인살리실레이트`(BHA 유도체)가 '살리실릭애씨드' 검색에 안 걸렸다.

→ 어간(`레티노`, `살리실`)으로 넓혔다. **한글 부분일치 함정 주의**: `레티노` 는 `레티놀` 을
못 잡는다. `놀`(ㄴㅗㄹ)과 `노`(ㄴㅗ)는 다른 음절 블록이라 라틴 알파벳처럼 접두사로 잘리지
않는다. 둘 다 넣어야 한다(테스트로 고정).

거짓 양성도 함께 막았다 — `부틸렌글라이콜`(흔한 보습제)이 Glycolic Acid 로,
`락토바실러스발효용해물`이 Lactic Acid 로 잡히면 안 된다.

### 남은 정리

**죽은 코드** — `recommend_products` 의 `analysis_mode == "body"` 분기와
`BODY_CARE_CATEGORIES`/`BODY_SAFE_INGREDIENTS`/`BODY_AVOID_PRODUCT_TERMS` 상수는
라우트가 `recommend_derma_care` 를 부르므로 도달하지 않는다.

## 7. 성분 확보 (2026-07-24 추가)

### 방법: 올리브영 상품정보제공고시

전자상거래 상품정보제공고시 + 화장품법에 따라 화장품은 **'화장품법에 따라 기재해야 하는
모든 성분'을 상세페이지에 표시할 법적 의무**가 있다. 판매자 재량이 아니라 법정 항목이라
커버리지가 높다.

```
GET /store/goods/getGoodsArtcAjax.do?goodsNo={goodsNo}&itemNo=001
```

상세 HTML(71KB) 대신 고시 블록만 3KB로 받는다. **curl_cffi 로 통과되며 헤드풀 브라우저가
필요 없다**(2026-07-24 실측).

응답은 `라벨 줄 → 값 줄` 구조라, 라벨 목록(`NOTICE_LABELS`)을 경계로 값만 잘라낸다.
경계를 안 두면 다음 항목 라벨("기능성 화장품 식품의약품안전처 심사필 여부")까지 성분에
섞여 들어간다.

### 함정: 스로틀링이 '성분 없음'으로 위장한다

지연 0.8초로 돌렸더니 약 60건에서 IP 스로틀에 걸렸는데, **HTTP 200 을 주면서 고시 본문만
비워서** 돌려준다. 이걸 그대로 기록하면 "이 상품은 성분이 없다"는 거짓 데이터가 조용히
쌓인다. 그래서:

- 빈 응답은 **3회까지 재시도**한 뒤에야 '성분 없음'으로 확정한다.
- 연속 실패/빈응답 6건이면 중단한다(재실행하면 이어서 진행).
- 기본 지연 2.5초. 0.8초는 확실히 막힌다.

### 한글 성분명 매핑

고시는 대한화장품협회 표준화 성분명(한글)으로 적힌다. `salicylic acid` 가 아니라

### 9.2 JP 성분: 라쿠텐 itemCaption

`scripts/enrich_ingredients_rakuten.py`. 결과: 277건 중 **136건 확보(49%)**, 요청 실패 0.

**파싱 함정 — 라쿠텐은 콜론이 아니라 브래킷을 쓴다.** 처음엔 `成分[:：]` 만 찾아서 확보율이
8% 였다. 실제 표기는:

```
原料・成分等【有効成分】ヘパリン類似物質…【その他の成分】精製水…
原料・成分等【成分】水、グリセリン、ミネラルオイル…
```

`原料・成分等` / `【成分】` / `【有効成分】` 를 시작 신호로 넣고, 섹션 종료 문자에서 `【` 를
빼자(그게 성분 블록 자체를 잘라먹고 있었다) **8% → 92%** 로 올랐다.

**매칭 게이트**: 엉뚱한 상품의 전성분을 붙이는 건 성분이 없는 것보다 나쁘다. 상품명
문자 바이그램 Jaccard ≥ 0.30 을 요구한다. 일본어는 띄어쓰기가 없어 토큰 분할이 불안정해서
바이그램을 쓴다. 정규화는 NFKC(전각 `３００ｍｌ` → `300ml`) 후 카타카나 블록 전체를 살린다
— `matsukiyo_matcher.normalize_key` 는 장음 `ー` 를 지워 `ボディローション` 을 조각낸다.

전체 확보율이 시험 구간(92%)보다 낮은 49% 인 이유: **아마존JP 의 긴 SEO 타이틀이 매칭에
실패**한다(73건). 마츠키요는 상품명이 깔끔해서 잘 맞는다.

## 10. 성분 어휘 확장 (2026-07-24)

### 발단: "올영 KR 2,800건 더 크롤하면 얼굴도 좋아진다"는 추정은 틀렸다

실측으로 반박됐다.

- 운영 DB 6,991건 중 **성분 없는 상품 1,297건은 전부 바디 계열**이다. 얼굴 상품은 0건 —
  얼굴 카탈로그 5,694건은 세포라 후보 CSV 의 `ingredients` 컬럼 덕에 처음부터 100% 였다.
- KR 카탈로그(3,165건)는 **런타임 버튼 매칭용**이라 상품 테이블 행이 아니다.
  goodsNo 직링크를 가진 DB 상품은 373건뿐.
- 성분 없는 1,297건을 KR 카탈로그에 이름 매칭하면 136건만 붙는다(10%). 나머지는
  아마존·세포라의 미국 상품이라 한국 카탈로그에 아예 없다.

→ **2,800건 크롤은 하지 않았다.** 근거 없는 작업이었다.

### 진짜 병목: 성분 어휘가 얼굴 액티브 위주였다

매칭된 136건을 실제로 크롤해 보니 고시 전성분은 정상적으로 나오는데(HTTP 200, 245~503자)
`INGREDIENT_RULES` 14종에 하나도 안 걸렸다.

```
이니스프리 한란 핸드크림 → 정제수, 부틸렌글라이콜, 시어버터, …
스킨푸드 허니 바디워시   → 계면활성제, 꿀추출물, 글리세린, …
바세린 바디밤            → 페트롤라툼(43.2%), 티타늄디옥사이드
```

기존 14종은 나이아신아마이드·살리실산·레티놀·비타민C 같은 **얼굴 액티브**다. 바디 제품은
**에몰리언트·오클루시브**로 구성된다. 페트롤라툼·콜로이달오트밀은 아토피 피부염에 근거
수준이 가장 높은 성분인데 시스템이 '성분 미상'으로 취급하고 있었다.

### 추가한 9종

`Glycerin` · `Petrolatum` · `Shea Butter` · `Squalane` · `Allantoin` ·
`Colloidal Oatmeal` · `Urea` · `Dimethicone` · `Jojoba Oil`

**targets 를 얼굴 점수가 아닌 `barrier`/`moisture`/`soothing` 으로 둔다.** 이유:
`severity_focus` 는 상품 타깃의 **평균**이라, 상품 82%에 든 글리세린이 얼굴 타깃으로 들어오면
랭킹이 통째로 뭉개진다.

여기에 얼굴 경로가 `product_targets` 를 `FACE_SCORE_TARGETS`(6개 점수 키)로 필터하도록 했다.
**현재 얼굴 성분 14종은 전부 얼굴 타깃이라 오늘 기준 no-op** 이고, 앞으로 어휘가 늘어도
얼굴 랭킹이 흔들리지 않는다. 테스트로 양방향을 고정했다
(`test_body_emollients_use_non_face_targets`).

### 부산물: stdout 이중 래핑 버그

`sys.stdout = io.TextIOWrapper(sys.stdout.buffer, ...)` 를 쓰는 스크립트를 다른 스크립트가
import 하면 이중 래핑이 되고, 먼저 만든 래퍼가 GC 되며 버퍼를 닫는다
(`ValueError: I/O operation on closed file`). `sys.stdout.reconfigure(encoding="utf-8")` 로
바꿨다 — 같은 객체를 바꾸므로 안전하다.

## 11. 실사용 버그: JP 지역 빈 추천 + DB 연결 (2026-07-24)

사용자가 실제 앱에서 바디 추천이 전 컬럼 "맞는 상품이 없어요"로 나오는 걸 발견. 두 겹의 원인.

### 11.1 진짜 원인: docker 백엔드가 빈 로컬 MySQL을 봤다

`docker-compose.yml` 의 backend 가 `DATABASE_URL` 을 로컬 mysql 로 **하드코딩**하고 있었다.
그 mysql 은 seed 데모(상품 25개)뿐이고, 오늘 적재한 카탈로그(6,991개, 바디 970개)는 전부
`.env` 의 **Supabase** 에 있었다. 앱은 빈 DB를 보고 있었던 것.

→ `DATABASE_URL: ${DATABASE_URL:-mysql+pymysql://...}` 로 바꿔 `.env` 를 상속하게 했다.
`docker compose up --build` 재빌드 필요(실행 중 컨테이너는 옛 코드/설정).

**교훈**: "추천이 비었다"의 1순위 용의자는 추천 로직이 아니라 **어느 DB에 붙어 있나**다.
docker vs run-backend(.env) 가 서로 다른 DB를 본다.

### 11.2 지역별 후보 필터

데이터가 있어도 JP 지역은 여전히 비었다. 추천된 바디 상품이 전부 KR 국내몰
(oliveyoung.co.kr)이고, JP 입점 리졸버가 그 링크를 전부 떼어내 프론트가 카드를 숨겼다.

- `product_market(url)`: 도메인으로 KR/JP/global/US 판정.
- `REGION_MARKETS = {kr: {kr, us}, jp: {jp, global}}`.
- `recommend_derma_care(region=...)`: 후보를 그 지역 구매 가능 상품으로 제한(비면 전체 폴백).
- 얼굴 추천은 스킨케어=글로벌 카탈로그라 이 필터를 적용하지 않는다(routes 가 "all" 로 호출).

### 11.3 JP 구매 버튼: 라쿠텐 직링크 캐시

지역 필터로 JP 후보는 마츠키요 상품이 되는데, `resolve_product_platforms(jp)` 가 그
원산지 링크마저 지워 버튼이 0개가 됐다(마츠키요는 라쿠텐·아마존JP 매칭이 잘 안 됨).

`enrich_ingredients_rakuten.py` 가 이미 각 JP 바디 상품을 라쿠텐 상품에 매칭하고 있었으므로,
그때 **itemUrl 도 저장**하도록 고쳤다(195건 전부 확보). `rakuten_body_links.rakuten_link_for`
가 요청 시점에 이름으로 조회해 라쿠텐 **직링크**를 붙인다. 라이브 검색
(`_verify_rakuten_for_skincare`, 초당 1요청 제한으로 상위 6개만)과 달리 API 재호출·레이트리밋
없이 매칭된 전부에 붙는다. 그래도 빈 상품은 `_backfill_native_body_link` 가 원산지(마츠키요)
링크로 최후 폴백.

### 11.4 성분 우선 원칙 (사용자 지시)

> "성분이 우선입니다. 성분이 없으면 상품을 추천하면 안 됩니다."

`recommend_derma_care` 의 `strict` 를 **항상 True** 로 바꿨다(이전엔 avoid 목록이 있는 질환만).
성분 데이터가 없는 상품은 (1) 질환 적합성 판단 불가 (2) 자극 성분 배제 불가라 추천에서 제외.
성분 '일치'는 여전히 가점(하드 게이트 아님)이지만, 성분 '존재'는 하드 요건이다.

부작용: JP 집중케어(body.treatment/oil)는 성분 보유 상품이 거의 없어 컬럼이 빈다. 이는
버그가 아니라 원칙의 결과다 — 근거 없는 추천보다 빈 슬롯이 낫다.

### 11.5 최종 검증 (실 HTTP, docker→Supabase)

| 컬럼 | KR | JP |
|---|---|---|
| 바디 세정 | 4건 · 네이버+올영 | 4건 · **라쿠텐 직링크** |
| 바디 보습 | 4건 · 네이버+올영 | 4건 · **라쿠텐 직링크** |

전 상품이 성분 근거 태그 보유(`Ceramide 함유` 등) — 성분 없는 상품 0건. 테스트 237 pass.

### 11.6 영유아·소아 피부 (질문 답변)

학습 데이터 확인 결과 **영유아·소아 데이터가 전무**하다:
- AI-Hub 03 성분 추천: 연령 13~60대(최소 13세).
- 바디 질환(dermatology): PAD-UFES·DermNet·Fitzpatrick17k = 전부 성인 피부과 데이터.

영유아 피부는 분포 밖(OOD)이고, 성인 기준 성분 추천(레티놀·AHA·BHA)을 적용하면 안 된다.
연령 분기 자체가 없다. 소아 대응은 별도 트랙(연령 게이트 + 소아 안전 성분 화이트리스트 +
소아 데이터)이 필요하다.
