## 1. 파이프라인

```
사진 → YOLOv8 네일 검출/정답라벨 → 크롭 → EfficientNet-B0 임베딩(1280d, L2정규화)
                                        ＋ 대표색(Lab/hex)
                                              ↓
                                  하이브리드 점수로 최근접 검색
                     score = cos유사도 − λ·(ΔE/100),  λ=0.5
```

**학습이 없다.** 사전학습 백본만 쓰므로 라벨이 없는 현 상황에서도 성립한다.

### 설계 판단
- **백본은 새로 받지 않았다.** 캐시에 있던 EfficientNet-B0(프로젝트가 피부·퍼스널컬러에 쓰는 것과
  동일)를 재사용해 스택을 일치시켰다.
- **손 크롭은 검출이 아니라 Roboflow 정답 폴리곤 라벨로 딴다.** 더 빠르고 정확하며, 받아온 라벨을
  실제로 쓰는 경로다. 발은 라벨이 0바이트라 검출로 간다.
- **대표색은 하이라이트를 뺀다.** 젤네일 정반사 때문에 그냥 평균내면 흰색으로 쏠려서,
  L 상위 15%를 제외하고 k-means 최대 클러스터를 대표색으로 삼는다.
- **32px 미만 크롭은 버린다.** 새끼발톱·초점흐림이라 임베딩이 무의미하다(279개 제외됨).

## 2. 인덱스 규모 (2026-07-28 중복제거 후 재빌드)

Roboflow v51 은 원본 3,626장을 7,025장으로 **증강**한 것이라, 같은 사진의 변형이 top-K 를
차지하면 "비슷한 디자인"이 사실상 같은 사진만 나온다. 파일명 `<원본>_jpg.rf.<해시>` 로 원본을
식별해 **원본당 1장만** 인덱싱한다(실측 58.6% 가 증강 사본 → 고유 원본 2,909개).

중복을 접은 만큼 손 이미지 제한(250장/split)을 풀어 **전량**을 넣었다.

| 항목 | 중복제거 전 | 후 |
|---|---|---|
| 크롭 총계 | 6,340 (발 3,913 / 손 2,427) | **15,504** (발 3,913 / 손 11,591) |
| 임베딩 | 31MB | 75.7MB |

> meta.json 이 참조하지 않는 고아 파일이 쌓여 번들만 커진다.

## 3. 정량 평가 — leave-one-design-out

같은 사진(디자인ID)에서 나온 크롭을 **전부 제외**하고 최근접을 찾는다. 같은 발의 다른 발톱을
맞히는 건 자명하므로 빼야 '다른 디자인을 제대로 찾는지'가 보인다. 질의 400개.

### 색 가중치 λ 스윕 (region=all)

| λ | ΔE(top-1) | color hit@5 (ΔE≤15) | 임베딩 유사도 |
|---|---|---|---|
| 0 (임베딩만) | 23.4 | 71.0% | 0.712 |
| 0.25 | 15.1 | 87.2% | 0.667 |
| **0.5 (채택)** | **11.4** | **96.0%** | **0.635** |
| 1.0 | 8.3 | 100% | 0.587 |
| 2.0 | 5.8 | 100% | 0.519 |

**중복제거·확장 후 재측정(λ=0.5, 질의 400개)** — 전부 소폭 개선:

| | 전(6,340) | 후(15,504) |
|---|---|---|
| ΔE(top-1) | 11.4 | **10.0** |
| color hit@5 | 96.0% | **98.2%** |
| 임베딩 유사도 | 0.635 | **0.642** |
| 랜덤 대비 색차 개선 | 75.2% | **76.0%** |

- 랜덤 베이스라인 ΔE는 **46.2** — λ=0 에서도 49.4% 개선, λ=0.5 에서 **75.2% 개선**.
- **λ=0.5 채택 근거**: 색 적중 96%를 얻는 대가로 임베딩 유사도는 0.712→0.635(−0.077)에 그친다.
  λ를 더 올리면 색은 맞지만 질감·패턴(글리터 vs 단색)이 뭉개진다.
- 부위가 바뀐 top-1(발↔손 교차)은 10.8% — 대체로 같은 부위 안에서 찾는다.

## 4. 육안 확인

발 검증셋 이미지로 질의(자기 디자인 제외):

- **보석·라인스톤 네일** → top-5 전부 다른 디자인의 보석/라인스톤 네일. 의도대로 동작.
- **플레인 화이트** → top-5 전부 화이트 계열, ΔE 3.4~10.6.
- **초점 흐린 크롭** → 유사도 0.16~0.25로 뚝 떨어짐. 낮은 유사도는 "자신 없음" 신호로 쓸 수 있다.

## 5. 한계

1. **디자인 카테고리 정답이 없어 "디자인이 맞았는지"는 색(ΔE)과 육안으로만 판정했다.** 프렌치/그라데이션/
   아트 같은 범주 정확도는 AI-Hub 04 메타데이터(범주 라벨) 확보 전까지 측정 불가.
2. Roboflow 손 데이터는 **대부분 민낯 손톱**이라 디자인 라이브러리로서의 기여는 낮다. 디자인이
   풍부한 쪽은 AI-Hub 발 데이터다. 손 디자인 커버리지는 AI-Hub 손 트랙(현재 0바이트)이 필요하다.
3. 인덱스에 증강 중복이 섞여 있다(Roboflow v51은 원본 3,626 → 7,025로 증강). 같은 원본의
   증강본이 top-K를 차지할 수 있어, 서빙 전에 원본 단위 중복제거가 필요하다.
4. ΔE는 CIE76(단순 유클리드)이다. 지각 균일성이 필요하면 CIEDE2000으로 교체.

## 7. 팔레트 브리지 — 시즌 ↔ 디자인 (같은 날 완료)

`PROFILES.makeup.nail` 은 **한국어 색이름만** 있어(라이브 검색 키워드용) 사진에서 뽑은 실제 색과
비교할 수 없었다. [nail_palette.py](../backend/app/services/nail_palette.py) 가 그 21개 이름에
hex 를 붙이고 Lab 으로 바꿔 ΔE 로 점수화한다.

- `nail_color_fit(lab, tone, subtype)` → 그 시즌에서 가장 가까운 색조 + ΔE + 0~100점
- `rank_seasons(lab)` → 색 하나가 어느 시즌에 맞는지 정렬
- sRGB→Lab 은 **cv2 없이 순수 파이썬**으로 구현(백엔드 의존성을 늘리지 않으려고)
- ⚠️ hex 는 색이름을 보고 정한 **근사치**(측색값 아님). 시즌 판정의 최종 근거로 쓰지 말고
  색 유사도 정렬·필터에만 쓸 것. 이름의 원본은 계속 `PROFILES` 다.
- 이름만 추가되고 hex 가 비면 **조용히 넘어가지 않고 KeyError** 로 터진다(테스트가 이걸 고정).

### 시즌별 커버리지 (인덱스 6,340개 기준)

민낯·클리어 크롭이 누드 계열 시즌을 부풀리므로 **채도 C\*≥15** 로 거른 뒤가 실제 수치다
(6,340 → 3,813개, 39.9% 제외).

중복제거·확장 전후(채도 필터 후 3,813개 → 9,526개):

| 시즌 | 전 | 후 | 배수 |
|---|---|---|---|
| 가을 웜 뮤트 | 1,707 | 5,900 (61.9%) | 3.5× |
| 여름 쿨 뮤트 | 1,690 | 5,408 (56.8%) | 3.2× |
| 가을 웜 딥 | 1,017 | 3,720 (39.1%) | 3.7× |
| 봄 웜 라이트 | 1,297 | 3,629 (38.1%) | 2.8× |
| 여름 쿨 라이트 | 1,358 | 3,422 (35.9%) | 2.5× |
| 겨울 쿨 딥 | 613 | **1,777** (18.7%) | 2.9× |
| **겨울 쿨 브라이트** | 489 | **767** (8.1%) | **1.6×** |

**빈 시즌은 없다.** 다만 **겨울 쿨 브라이트는 절대 수만 늘고 비율은 12.8% → 8.1% 로 오히려
떨어졌다** — 전체가 더 크게 늘었기 때문이다. 선명한 쿨 레드·푸시아 디자인 자체가 데이터에
드물다는 뜻이라, 인덱스를 키우는 것으로는 해결되지 않는다. 상품 추천으로 넘길 때는 라이브
검색이 이 부족분을 메워야 하고, 근본 해결은 **겨울 계열 디자인 소스를 따로 확보**하는 것이다.

육안 확인: 겨울 쿨 브라이트 top-10 → 전부 선명한 레드·푸시아. 의도대로 동작.

## 8. API·프론트 연결 (같은 날 완료)

`POST /api/analyze-nail-design` (multipart `image`, `top_k`) → 검출된 네일별 유사 디자인 top-K
(썸네일은 **base64 data URI**로 동봉 — 정적 파일 라우트를 새로 열지 않으려고) + 시즌 적합도 7개
+ `recommended_shades`.

- **상품 추천은 이 API가 하지 않는다.** `recommended_shades` 가 `PROFILES` 의 네일 색이름
  그대로라, 프론트가 기존 item-match 라이브 검색에 그대로 넘기면 된다(상품 파이프라인 중복 방지).
- **모델·인덱스가 없으면 500 이 아니라 `feature_available=false`** 로 응답한다(다른 AI 모듈과 동일 규약).
  배포에서 네일 자산을 빼도 앱이 죽지 않는다.
- 프론트: 홈 '추후 추가' 카드를 **'네일·페디 디자인'으로 교체·활성화**([App.tsx](../frontend/src/App.tsx)),
  `nail-design` 모듈 신설(사진 업로드 → 대표색 → 비슷한 디자인 → 시즌 적합도 바 + 추천 색상 칩).

### ⚠️ 임베딩 백본을 로컬 체크포인트로 굳혔다

인덱스를 만들 때 쓴 `weights=IMAGENET1K_V1` 은 **런타임에 인터넷 다운로드**를 일으킨다. 이 프로젝트의
다른 모델은 전부 `weights=None` + 로컬 체크포인트라 규약도 어긋난다.
→ 같은 가중치를 `data/models/nail_embedder_efficientnet_b0.pt` 로 저장하고 그걸 읽는다.
저장 전후 임베딩 **최대 오차 0.0** 이라 기존 인덱스는 그대로 유효하다(재빌드 불필요).

### 알고리즘 원본을 백엔드 서비스로 옮겼다

`app/services/nail_design_index.py` 가 `dominant_color`·`Embedder` 의 원본이고, 빌드/질의 스크립트가
이걸 import 한다. 빌드와 서빙이 다른 구현을 쓰면 같은 사진에서 다른 색·임베딩이 나와 검색 품질이
조용히 망가진다. 리팩터 후 동일 질의 결과가 비트 단위로 같음을 확인했다.

## 9. 정확도 측정 — 사람 판정 도구

지금까지의 수치(ΔE·color hit)는 **색**만 본다. "디자인이 비슷한가"는 범주 라벨이 없어 기계로
잴 수 없으므로 소량을 사람이 판정한다. [review_nail_retrieval.py](../scripts/review_nail_retrieval.py):

```bash
python scripts/review_nail_retrieval.py --make --samples 30
#   → docs/nail_retrieval_review.html (썸네일 내장 자체완결, 1.5MB)
#     브라우저에서 '비슷함' 체크 → [CSV 저장]
python scripts/review_nail_retrieval.py --score <내려받은.csv>
#   → precision@1 / hit@5 / 평균 precision@5 / MRR
```

- 질의는 채도 C\*≥15 크롭에서만 뽑는다(민낯은 '디자인'으로 보기 어려움).
- 같은 사진(디자인ID)의 크롭은 후보에서 제외 — eval 과 같은 규약.
- 애매하면 체크하지 않도록 안내해 **보수적으로** 재게 한다.
- CSV 는 `utf-8-sig` 로 읽는다(엑셀로 저장하면 BOM 이 붙어 첫 헤더가 깨진다).

**아직 사람 판정은 수행되지 않았다** — 시트만 준비된 상태다.
